How the JavaScript event loop actually schedules your code

May 22, 2026

"JavaScript is single-threaded" is one of those true statements that stops being useful the moment you try to reason about a real program. A real program has timers, fetch calls, promise chains, DOM events, and a render pipeline, and somehow they all coexist on that one thread without obviously stepping on each other. The thing that makes it work is the event loop: a small, almost boring piece of machinery in the runtime that decides what runs next.

This is a deep dive into how that machinery actually behaves. We'll walk through the call stack, the host's task and microtask queues, the render step, and the small ordering rules that explain why setTimeout(fn, 0) can run after a promise callback even when the promise resolves later in source order.

The call stack

Every running JavaScript program has a call stack. When you call a function, a stack frame is pushed; when the function returns, the frame is popped. While there are frames on the stack, the engine is busy and cannot pick up new work. 

function outer() {
  inner();
}

function inner() {
  console.log('hi');
}

outer();
// stack: [outer]
//        [outer, inner]
//        [outer, inner, console.log]
//        ... unwinds back to empty

The rule that ties everything else together: the event loop will not pick up new work while the stack is non-empty. Long-running synchronous code blocks the loop. Everything we are about to discuss happens between stack-empty moments.

The host environment

The JavaScript language spec itself does not define setTimeout, fetch, or addEventListener. Those are provided by the host — the browser, Node.js, Deno, or whatever embeds the engine. When you call setTimeout(fn, 1000), the engine hands fn off to the host with a "wake me in a second" instruction. The engine itself goes back to processing the stack.

A second later, the host doesn't just call fn directly — it can't, because the engine might be busy. Instead it enqueues a task (sometimes called a "macrotask") on a task queue. The event loop will pick it up at the next safe moment.

Tasks vs microtasks

There are two queues, and the distinction is the single most important thing to internalize.

  • Task queue — fed by setTimeout, setInterval, I/O completion, DOM events, postMessage, and similar host-driven sources. One task runs per loop iteration.
  • Microtask queue — fed by resolved Promise callbacks, queueMicrotask, and MutationObserver. The loop drains this queue completely after every task, before doing anything else.

The pseudocode for one tick is roughly: 

while (true) {
  const task = taskQueue.shift();   // pick one task
  if (task) run(task);              // run it to completion
  while (microtaskQueue.length) {   // drain ALL microtasks
    run(microtaskQueue.shift());
  }
  if (shouldRender()) render();     // maybe paint
}

A worked example

Here is the canonical puzzle. Predict the output before reading on: 

console.log('A');

setTimeout(() => console.log('B'), 0);

Promise.resolve().then(() => console.log('C'));

queueMicrotask(() => console.log('D'));

console.log('E');

The output is A E C D B. Walking it through:

  1. 'A' — synchronous, runs immediately.
  2. setTimeout(..., 0) — the host schedules a task. It does not run yet.
  3. Promise.resolve().then(...) — the promise is already resolved, so its callback is enqueued on the microtask queue.
  4. queueMicrotask(...) — another microtask, queued after the promise one.
  5. 'E' — synchronous, runs immediately.
  6. The stack is now empty. The loop drains microtasks before anything else: 'C', then 'D'.
  7. Now the loop picks the next task — the timeout callback — and runs 'B'.

Why this ordering matters

The microtask queue is drained fully on each tick, which means a microtask that enqueues another microtask will run before the next task. This is incredibly useful — it's how promise chains feel synchronous — but it is also a footgun. 

function loop() {
  Promise.resolve().then(loop);
}

loop(); // browser tab freezes: render never gets a chance

That code creates an infinite microtask chain. Because the loop must drain microtasks before painting, the page never repaints and the tab effectively hangs. The same code written with setTimeout(loop, 0) would still be wasteful but would let the browser render between iterations, because each timeout is a fresh task and rendering happens between tasks.

Where rendering fits

On the browser side, the event loop also coordinates with the renderer. After a task finishes and microtasks have drained, the host may choose to perform a "rendering" step: style recalculation, layout, paint, and any requestAnimationFrame callbacks. Rendering does not happen between microtasks, which is exactly why a microtask flood freezes the UI.

The practical guidance falls out of this: if you want code to run "as soon as possible but after the current operation finishes," use queueMicrotask. If you want it to run "soon, but let the browser breathe (render, handle input) first," use setTimeout(fn, 0) or requestAnimationFrame.

A mental model you can keep

When you read async code, mentally substitute this three-step loop:

  1. Run one task to completion (which may include lots of synchronous code and may queue more tasks or microtasks).
  2. Drain every microtask, including any new ones spawned along the way.
  3. Optionally render. Repeat.

That model is enough to reason about almost every promise vs. timer vs. event-handler ordering question you will hit in practice. The exotic edge cases — task source priorities, starvation, integration with worker threads — are refinements on top of it, not contradictions of it.

Once you see code through this lens, the language stops feeling magical and starts feeling mechanical. Which is, I think, the best thing you can ask of any runtime.
